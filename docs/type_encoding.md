# Model-owned atom encodings

Each model must use the element representation it was trained with. PCA is not
uniquely determined by its dimension: nearly degenerate components can change
with numerical libraries or CPU thread counts. Rebuilding a PCA table at inference
can therefore reinterpret the same continuous outputs as different elements.

## Normal workflows

- **Fresh training:** `src/train_crystalite.py --type_encoding subatomic_tokenizer_pca_16 ...`
  builds a table once and embeds that actual state in every checkpoint (best,
  step/epoch latest, and final). PCA-8/24 and raw descriptors work the same way.
  The known M0 table is never substituted into a new training run.
- **Sampling and evaluation:** existing commands automatically restore the model's
  `type_encoding_state`. No thread-count workaround or private artifact directory
  is needed. Source, schema version, and state/table hashes appear in the logs and
  JSON reports. Dataset-dependent allowed-element masks and atom-count distributions
  retain their existing behavior; the MP20 training split is still required when
  reproducing the historical empirical-count sampling recipe.
- **Crysfinity `--init_from`:** restores the parent checkpoint's encoding before
  encoding training inputs. An explicitly conflicting `--type_encoding` fails.
  Architecture arguments must still match the parent model. The optimizer remains
  fresh, as before; this is not a full optimizer/RNG resume facility.
- **Synthetic augmentation:** the generator uses its own checkpoint's encoding,
  independently of the model subsequently trained on the generated structures.

The two released CSP models, `csp_mp20_best.pt` and `csp_mpts52_best.pt`, use
`atomic_number` with 95 channels. They need no PCA artifact or migration. Legacy
non-PCA checkpoints continue to load. Newly trained models record their encoding
configuration, and descriptor-based models also save their numerical tables.

## Legacy M0 and migration

Both repos include the approximately 33 KB `src/models/encoding_assets/m0_pca16_v1.pt`
and a registry. The resolver uses this table only after fingerprinting both model
and EMA tensors against the verified step-1,325,000 M0 weights. The original
atom-reps checkpoint, converted Crystalite checkpoint, and Snellius `dng.pt` have
different file hashes but identical model/EMA tensors. Names and dimensions alone
never select a recovered table.

Verified M0 identifiers:

```text
model + EMA fingerprint (schema v1):
12052869a9ae1c047132d2373d4f97101a7f6bcb3dfb6035b8a9cdaaf5f9a136
encoding state SHA-256:
b2008b4a7a4c7d2aa760b8813f742cb0c406d0293e5b26244fde901564e1ea06
snap_table float32 bytes SHA-256:
b8cc20385c514aa45de6ee0068776fedd7d72d3981bcc9507e5de1e267cfb9e1
```

The recovered state was checked against the recorded training source and startup
statistics for [W&B run kny9rodv](https://wandb.ai/ai_ecg/DNG_MP20/runs/kny9rodv)
(training commit `00e3f08468da6f6b400fdacee1279337530c0744`). A subsequent H100 replay
matched 2,048 archived round-0/1 structures, including all 21,390 atom labels and
the coordinate/lattice tensors. Recovered and native tables decoded the same
continuous outputs identically. This is a verified reconstruction; the original
training checkpoint did not contain the table itself.

To prepare a self-contained checkpoint, write to a new destination:

```bash
# Crystalite
python src/convert_atom_reps_ckpt.py \
  --input best.pt --output best_with_encoding.pt --verify-load

# Crysfinity
python scripts/migrate_dng_checkpoint.py \
  --src dng.pt --dst dng_with_encoding.pt
```

Both commands preserve model and EMA tensors. They reject overwriting the source
(including symlink/hard-link aliases). Replacing an existing destination requires
`--overwrite`; writes publish a complete file only after serialization finishes.
A migrated checkpoint uses embedded state and no longer needs the M0 registry.
Existing encoding state is validated and preserved through conversion.

**An unrecognized legacy PCA checkpoint fails to load.** Recover and independently
verify its original encoding, then supply a portable state artifact with
`--type-encoding-state recovered_state.pt` to the appropriate migration command.
The artifact must use the schema below and include
`provenance.checkpoint_weights_sha256`, generated by
`checkpoint_weights_sha256(checkpoint)` after establishing the historical match.
A matching checksum proves the binding to those weights, not the scientific
provenance of an arbitrarily chosen table. Encoding renames, current PCA
recomputation, or copying the M0 table into unrelated models are not recovery.
There is no opt-in to silently recompute an unknown legacy PCA table.

## Checkpoint format and developer integration

`type_encoding_state` is a plain dictionary containing:

- `format_version: 1`, `encoding_state`, explicit `element_order`, `state_sha256`,
  and descriptive `provenance`.
- Encoding name, vocabulary and feature dimensions; for descriptors, group slices,
  means/stds, weighted descriptors, prototype norms, `z_to_enc`, and `snap_table`;
  for PCA, the actual components and explained-variance arrays as well.
- CPU float32 tensors and simple scalar/list/dictionary metadata. Group slices are
  stored as `[start, stop, step]`. Standalone artifacts load with `weights_only=True`.

The canonical state hash covers version, numerical state and element order. Tensor
hashes include dtype, shape and exact bytes; descriptive provenance is excluded.
The separate `snap_table_sha256` report field hashes just contiguous float32 bytes
for comparison to the historical audit. Corrupt, inconsistent, or unsupported
embedded states fail; they never trigger a fallback.

Use `training_type_encoding` for training and `resolve_type_encoding` for all
checkpoint consumers. Use `export_type_encoding` when saving. Do not call
`build_type_encoding` to reconstruct a PCA encoding from checkpoint metadata.
Both repos implement the same schema and include cross-repo regression checks.

## Reproducibility boundary

Saving the encoding fixes its meaning across machines. It does not guarantee
bitwise-identical diffusion trajectories on different GPU architectures or
numerical environments. Record seed, steps, precision, chunk size, dataset,
allowed elements, hardware and software alongside the encoding hash. The earlier
roughly 3% atom disagreement in the corrected Ada-versus-H100 replay was in sample
generation; the same fixed continuous outputs decoded identically with the
verified tables.

This code change does not repair already saved round-2 decoded labels or rerun
relaxations. The existing archives remain historical results.
